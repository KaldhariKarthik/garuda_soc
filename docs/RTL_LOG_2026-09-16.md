## 0. Status in one paragraph — read this before anything else

Ten blocks of RTL now exist, are wired together in `garuda_soc_top`, and sit
under `garuda_chip_top` which generates the chip's own clocks and resets. All of
it **compiles, simulates and synthesises**: six testbenches run **1,007 checks
with 0 failures**, and the whole chip synthesises to 50,535 cells with **zero
latches inferred**. That is a real result and it is also a narrow one. Everything
was run under **Icarus Verilog and Yosys only** — not the team's Xcelium signoff
flow, not gate-level, no coverage collected, no SDC and no timing analysis of any
kind. The testbenches were written by the same hand, at the same sitting, from
the same reading of the specifications as the RTL, which is the weakest thing
about this result and is discussed in §6. All seventeen check failures seen along
the way were defects in the **testbenches**; not one was an RTL defect. Section 7
states precisely what is and is not proven.

## 3. Two specification defects found by implementing the specifications

Both in `docs/BUGS.md` §2b in full. Both were found by **writing** the RTL, and
both now have a **passing test that would fail without the fix**.

### BRG-1 — the bridge as specified drops every second back-to-back access

Bridge §7.5 says the bridge accepts a new transaction "only from `H_IDLE`". But
`H_RESP_OKAY` and `H_ERROR_2` both drive `HREADYOUT` high — they must, that is
how a transfer completes — and a high HREADY is by definition the condition under
which the master's next address phase *is accepted*, that same cycle. Implemented
literally, the master moves on while the bridge ignores the access: it never
reaches APB, no error is raised, and the master reads stale data. Firmware
configuring a peripheral with consecutive stores — how the DMA and CLIC are
programmed at boot — would lose every second write.

Fixed by qualifying acceptance on `hreadyout_o` rather than on one state.
Verified by `tb_ahb2apb` T8, which issues 8 back-to-back transfers and requires
the APB model's own access counter to read 8. **Passes.**

### CRG-1 — a one-cycle watchdog pulse asserts the whole chip's reset for 5 ns

CRG §7.1 combines the reset sources as a bare term, so Block 19's one-cycle pulse
asserts the entire chip's reset for one hclk period. Across a buffered reset tree
on a 1.45 mm die that risks a *partial* reset — some flops cleared, some not —
indistinguishable from corrupted state.

Fixed by stretching the request to 16 hclk cycles, with the stretch counter reset
by `por_n_i` only, never by its own output. Verified by `tb_crg` T9. **Passes.**

## 3b. One RTL defect found by lint — and a correction to this log

**Correction first.** An earlier revision of this log stated that no lint had
been run and that Verilator "aborts on this Windows/MSYS setup". That was wrong,
and the error was mine twice over: the first two attempts *did* abort, I filtered
the output for specific warning classes, found none, and reported the new blocks
"lint-clean" — a clean result produced by a tool that had never read a line of
source. That is the same false-PASS shape as TOOL-4, TB-11 and TOOL-5.

The fix was already written down in this repository. `docs/BUGS.md` **TOOL-2**,
recorded during the DMA session, says Verilator in the portable bundle needs
`VERILATOR_ROOT` set and takes `+incdir+path`, **not** `-I path` — with a space
it parses the sources as top-module names, which is exactly the
`Cannot find file containing module: 'rtl/clic/clic_source_cond.v'` seen here.
The lesson is not about Verilator: **the defect register already contained the
answer and was not consulted.**

**The defect it then found — CLIC-1.** `rtl/clic/clic_apb_regs.v` indexed six
arrays of `CLIC_N` (32) entries with `idx[9:0]`, a 10-bit value, at ten sites:

```
%Warning-WIDTHTRUNC: clic_apb_regs.v:143: Bit extraction of var[31:0]
                     requires 5 bit index, not 10 bits.
```

It was harmless in the current design only because `idx_ok` gates every write
and the read mux, so an out-of-range index never reaches the arrays. It is still
a real width defect, and precisely the class a 10-bit index silently truncating
onto a 5-bit array is expected to produce once anyone changes `CLIC_N` or the
qualification.

**Fix:** a properly sized `aidx = idx[IDX_W-1:0]` with
`IDX_W = $clog2(CLIC_N)`, used for array indexing only. `idx` stays 10 bits
because the *range check* must see the full offset — narrowing it there would
fold a stray address back onto a live source, the exact failure `idx_ok` exists
to prevent. No architectural change; no behavioural change.

**Confirmed after the fix:**

| Check | Before | After |
|---|---|---|
| Verilator `WIDTHTRUNC` in `clic_apb_regs.v` | 7+ | **0** |
| `tb_clic` | 33/33 | **33/33, 0 failures** |
| `clic_top` synthesis | 3,449 cells | **3,322 cells**, 0 latches |
| Full regression | 1,007 / 0 | **1,007 / 0** |

The cell count *fell* by 127 because the narrower index removes width-extension
logic — which is also why the whole-chip figure in §5 moved.

**Left standing, per block, with reasons:**

| Warning | Where | Why it stays |
|---|---|---|
| `UNUSEDSIGNAL` | `pwdata_i[31:8,4:2]` (CLIC), `haddr_i[31:16]` / `htrans_i[0]` (bridge), `dp_addr[31:16]`, `arr_addr[13:12]` (memory) | Reserved register bits, the region nibble consumed upstream, and the BUSY/IDLE distinction deliberately unused. All documented in the file headers. |
| `SYNCASYNCNET` | `rst_n_i` (CLIC), `hreset_n_i` (memory), `sync_q` (clk_div) | A reset used both as an async reset and as a condition in ordinary logic. In `clk_div` this is the §4.4.2 strap-freeze, which is specified behaviour. |

`reset_ctrl` lints completely clean. The trailing `%Error: Exiting due to N
warning(s)` line is Verilator's summary, not an error — `reset_ctrl` emits it
with zero findings and `rc=0`.

catches, so the check has to be the real one.

small register files; only one touches new code (`clic_apb_regs` level array).

## 6. All seventeen failures were testbench defects — and that is a warning

The first run of every new testbench failed. Not one failure was an RTL defect:

| Testbench | Initial failures | Cause |
|---|---:|---|
| `tb_crg` | 4 + a hang | always-block race; absolute-time modulo; wait armed after the event |
| `tb_ahb2apb` | 2 | `PENABLE && !PSEL` is invalid on a shared-PENABLE bus |
| `tb_clic` | 7 | latency sampled one edge early; stale source held high; wrong expectation of level re-fire |
| `tb_soc_ahb` | 1, then 2 | transient sampled at end of run; then asserting an interrupt the firmware had disabled with `CR.IE=0` |

All are logged as TB-16…TB-21 and TOOL-5. Three recurring shapes, all previously
seen in this project:

- **A check that can pass by doing nothing.** The static checker reported "0
  errors" having matched zero instantiations. That is TOOL-4 and TB-11 wearing a
  third set of clothes, and it is now the most recurrent defect class in the
  register. It was fixed by counting the work done and failing on zero, then
  validated against deliberately corrupted RTL before its results were believed.
- **A monitor that cries wolf on legal traffic** (TB-19, and TB-15 before it).
  Worse than no monitor: the next real violation lands in a log people ignore.
- **A stale artifact reported as a result.** One SoC "run" replayed an old
  binary because the compile had failed and `vvp` ran the previous `.vvp`. The
  runner now deletes the binary first and refuses to run if the compile fails.

**This is the honest caveat on the whole result.** These testbenches were written
by the same hand, at the same sitting, from the same reading of the
specifications as the RTL. A test and an implementation that share an author
share the author's misreadings — so "1,007 checks, 0 failures" means the RTL
agrees with one person's interpretation, not that it is correct. The failures
above are evidence that the testbenches were *less* trustworthy than the RTL, not
more. Independent verification still has to happen: the team's Xcelium flow, a
second engineer's directed tests, riscv-arch-test, and a golden reference model.

## 7. What is proven, and what is not

**Proven:**

- It compiles. 3,654 lines of new RTL through a real Verilog parser, zero errors,
  and the wired SoC elaborates from 80 sources.
- It simulates. 1,007 self-checking assertions across six testbenches, 0 failures,
  including the memory aliasing test, the bridge's two-cycle ERROR and
  back-to-back acceptance, CLIC strict-greater threshold and level re-fire, the
  CRG bootstrap and fallback frequency plan, and a full SoC boot.
- It synthesises. Whole chip, no errors, `check -assert` clean, **zero latches**.
- Block 6 regression intact: 796 checks still pass against the unchanged models.

**Not proven:**

- **One simulator, one synthesiser.** Icarus and Yosys only. Never compiled by
  Xcelium or VCS, which is the signoff flow and will find things these do not.
- **Lint is per-block only, not whole-chip.** Verilator runs (see §3b) when
  invoked per directory. It does **not** work against the expanded filelist:
  the `rtl/core/...` paths get concatenated onto each `+incdir+` prefix and it
  fails to open them, so there is **no chip-level lint**. Cross-module width
  and connectivity issues spanning block boundaries would not be caught.
- **Two Verilator warning classes are left standing deliberately** (§3b):
  `UNUSEDSIGNAL` on reserved register bits and unused address slices, and
  `SYNCASYNCNET` where a reset is both an async reset and a condition in
  ordinary logic. Both are documented design facts, not deferred work.
- **No gate-level, no coverage, no timing.** No SDC exists. The ≈2.8 ns array
  path, the 200 MHz arbiter tree and the ≈6 pclk bridge latency remain analytic.
  Yosys cell counts say nothing about whether 200 MHz closes.
- **The interrupt path never fires.** It is wired and continuously checked for
  correct connection, but `soc_dma_smoke.S` sets `CR.IE=0`, so no interrupt is
  ever taken. End-to-end needs a boot image with `CR.IE=1`, a CLIC level
  programmed over APB, and an ISR. **This is the most obvious next test.**
- **The memory arrays are not the real arrays.** Behavioural stand-ins until the
  PDK compiler macros land (MEM §13.6, still FLAGGED).
- **The ISRAM was never selected** in the SoC run (`selects ISRAM=0`) — the smoke
  program runs from ROM and never exercises the boot copy into instruction
  memory. Block 3 is proven at block level only.
- **Fallback mode is untested above block level.** `tb_crg` covers the divider;
  no SoC run has been done at 100 MHz.

## 9. How to run it

```bash
make test_crg test_mem test_bridge test_clic   # block level
make test_soc_ahb                              # the wired SoC
make synth                                     # chip: structural + latch check

# without Cadence, same filelists:
./scripts/run_sim.sh tb_crg
./scripts/run_synth.sh garuda_chip_top
```

**Toolchain note.** This machine had no simulator or synthesis tool. Chocolatey
could not install one (no admin rights, and `yosys` is not a Chocolatey package),
so the OSS CAD Suite was extracted into a **session temporary directory**, which
will not survive. Two things caught anyone repeating this: the binaries need the
execute bit set after extraction, and both `bin` **and** `lib` must be on `PATH`
or `vvp` and `yosys` fail with missing-DLL errors while `iverilog` works fine.
For a permanent install, put the suite somewhere stable and add it to
`scripts/setup_env.sh` alongside the Xcelium paths.
