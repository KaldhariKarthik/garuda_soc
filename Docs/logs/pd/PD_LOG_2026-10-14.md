# GARUDA: exploratory ASAP7 implementation flow, 2026-10-14

**What this is.** The record of the first end-to-end exploratory physical-design run of GARUDA on
ASAP7 (mock memories, floorplan, place, CTS, route, finish), under the standing approval of
2026-10-13/14.

**What it is not.** Timing closure, a 28 nm statement, or an SRAM estimate. Every memory area and
timing figure comes from PD-only mock models; I/O budgets and the derived-clock uncertainty are
provisional assumptions (PD_LOG_2026-10-13 §§4, 6, 8).

Repo `main` @ `e43672f` plus the uncommitted P1/P2/P3 RTL edits and PD files (nothing committed or
pushed). Tools as in `flow/pd/TOOLS.md` (ORFS `3451ca1`, OpenROAD `26Q4-110-g91e5f5ff2f`, Yosys
0.68+ `a5af9d690`; YosysHQ Yosys 0.68 / SBY v0.68 / z3 4.8.12 for formal).

## 1. Mock memory models (`flow/pd/asap7/mock/`)

`garuda_mock_srams.v` holds `garuda_sram_16384x32`, `garuda_sram_4096x32` and `garuda_rom_1024x32`.
Their ports are identical to P3's macro instances, and their behaviour matches
`sram_wrapper`'s behavioural model (ce gating; read when ce & !we, registered and held; per-byte
writes on be[3:0]), except that each has **4 rows**, with the address XOR-folded into a 2-bit row
index so that every pin stays live (addresses alias). The ROM mock returns 4 arbitrary constants
and **does not contain the boot image** (the real ROM gets it at the foundry stage).

Formal check (`mock_props.sv`, `mock_props.sby`; run from a copy in `~/tools/garuda_pd/mock_formal`,
log `~/tools/logs/b3_mock_formal.log`). Against a shadow built from the inputs for one arbitrary
row: P1 read-back with byte enables, P2 rdata held without a read, P3 ROM contents and hold.

| Task | Result |
|---|---|
| rom_prove | **PASS, unbounded** (k-induction, basecase and induction pass) |
| isram_cover / dsram_cover | PASS: a byte-masked write followed by a read of the probe row is reachable (step 3) |
| isram / dsram, k-induction (first run) | basecase PASS to depth 6; induction step FAIL: the shadow property is not inductive without an invariant on the mock's internal array (not referenceable across the hierarchy). Not a design failure |
| isram_bmc / dsram_bmc | **0 failures through step 6** (6 cycles); the depth-12 target was stopped by the 20-min run cap (exit 124) |

So the RAM mocks are **bounded-checked to 6 cycles** (two masked writes, a read and the check
fit), not proven unbounded. The ROM mock is proven.

## 2. Hierarchical configuration

- Blocks (`flow/pd/asap7/<block>/config.mk` + `block_common.mk`): die forced to the approved sizes
  (133.488 × 166.6, 33.372 × 166.6, 16.686 × 83.3 µm), core inset 1 µm, routing M2–M4 only, pins
  on the right edge (M4, `mock/io_right.tcl`), `BLOCK_grid_strategy.tcl` PDN. Block SDC
  `mock/block.sdc`: clk 4000 ps (hclk at DIV2) plus ORFS's generic ASAP7 macro template (80 ps
  max_delay optimisation targets).
- Parent (`flow/pd/asap7/config.mk`): `BLOCKS` = the three mocks (ORFS adds their LEF and lib
  automatically; the stubs are used only when `BLOCKS` is empty); `SDC_FILE` =
  `garuda_div2.sdc` (primary); `DIE_AREA 0 0 320 300`, `CORE_AREA 5 5 315 295` (approved
  start); `MACRO_PLACEMENT_TCL` = `macro_place.tcl` (six macros in one row along the bottom, 4 µm
  pin channels, snapped to the 0.054/0.27 µm grid); `PLACE_DENSITY 0.45`.
- Config dry-check (`~/tools/logs/b3_cfgcheck.sh`): ORFS resolves all of the above.

## 3. Runs (each in its own FLOW_VARIANT under `~/tools/garuda_pd/`; driver `~/tools/logs/b3_flow.sh`)

### pnr_r1 (default ORFS CTS)
- Blocks: all three mock blocks completed `generate_abstract` (ISRAM, DSRAM, ROM). GARUDA
  synthesis passed and the ODB now loads (the macro LEFs exist).
- First stop: `[ERROR FLW-9001] macro_place.tcl: instance …g_bank[0]… not found`. A script defect:
  OpenDB stores the `[n]` in instance names escaped. Fix: `macro_place.tcl` now selects the macros
  by master name and places them with `setLocation`/`FIRM`. Placement: ISRAM (7.02, 7.02), DSRAM0–3
  at x = 144.558 / 181.98 / 219.402 / 256.824, BROM at 294.246; all y = 7.02 µm.
- Resumed: floorplan and placement OK. **CTS: OpenROAD crashed (Signal 11, exit 245) inside
  `repair_timing` hold repair** after `[INFO RSZ-0046] Found 1702 endpoints with hold
  violations`, worst −2630.8 ps at `u_reset_ctrl.prst_q[1]/RESETN`.

### pnr_r2: attempt 1, `SKIP_CTS_REPAIR_TIMING=1` (diagnostic), to CTS
CTS completed (18 min 54 s wall time including blocks; peak 2.1 GiB, 0.4 GiB swap). Analysis
(`~/tools/garuda_pd/analysis/pnr_r2_cts_skew.log`): each clock tree is well balanced (aon 68–87,
hclk 189–236, pclk 178–230, tck 137–159 ps; intra-clock skew ≤ 43 ps), **but CTS-0033 "Balancing
latency for clock aon_clk" inserted 116 `delaybuf_*_aon_clk` buffers (≈ 2.1 ns) on the aon_clk
branch feeding the hclk mux.** That delays hclk and pclk by ≈ 2.1 ns relative to aon_clk. Worst
hold: `u_reset_ctrl.sys_req_q` (aon) → `prst_q[1]/RESETN` (pclk) removal, −2637.66 ps; pclk group
`u_bridge.u_fsm.rdata_o[4]/D` −2555 ps. A setup miss at `t1_q/D` (refclk group, −352 ps) was
repaired to +3.5 ps by CTS repair in pnr_r1/r3.

### pnr_r3: attempt 2, `CTS_ARGS=-sink_clustering_enable -repair_clock_nets -delay_buffer_derate 0`
No change: CTS-0033 still inserted 112 delay buffers (213 in total), again 1702 hold violations,
and the same crash. `-delay_buffer_derate` does not gate this balancer.
Source (`tools/OpenROAD/src/cts/src/TritonCTS.cpp:2747`): `balanceMacroRegisterLatencies()` runs
only when `insertionDelayEnabled()`, i.e. it is turned off by `-no_insertion_delay`.

### pnr_r4: attempt 3, `CTS_ARGS=-sink_clustering_enable -repair_clock_nets -no_insertion_delay`
**CTS fixed.** No CTS-0033 latency balancing; `[INFO RSZ-0046] Found 1747 endpoints with hold
violations` (now small), repaired: `[INFO RSZ-0032] Inserted 3240 hold buffers`, final hold WNS
+0.004 ps, TNS 0, area +0.4 %; no crash (TOOL-18 did not recur). Run continued from CTS to finish
with the same settings (driver `~/tools/logs/b3_r4.sh`, `TARGET=finish`). To make the fix
permanent, `CTS_ARGS` should go into `flow/pd/asap7/config.mk` (done after the run; see §4).

**pnr_r4 routing failed** at global route (`do-5_1_grt`, Error 1): `[ERROR DRT-0073] No access
point for …u_macro/addr[0]` on the ISRAM and all four DSRAM macros (7 errors), plus many
`[WARNING DRT-0419] No routing tracks pass through the center of Term` on the BROM pins. Cause
(BUGS PD-8): `macro_place.tcl` snapped the origins only to the 0.054 µm site / 0.27 µm row grid
(y = 7.02 µm). The block pins sit on the block's own 0.048 µm M4 tracks, so in the parent every pin
was 0.012 µm off track (M4: offset 0.012, pitch 0.048; `platforms/asap7/openRoad/make_tracks.tcl`).

## 4. Fix and pnr_r5
- `flow/pd/asap7/config.mk`: `CTS_ARGS ?= -sink_clustering_enable -repair_clock_nets -no_insertion_delay` (PD-7 made permanent).
- `flow/pd/asap7/macro_place.tcl`: origins snapped to x = n·0.432 µm (lcm of 0.036, 0.048 and the 0.054 site) and y = n·2.16 µm (lcm of 0.036, 0.048 and the 0.27 row); gap still 4 µm.
  Expected origins: y = 8.64; x = 5.616 (ISRAM), 143.424, 181.008, 218.592, 256.176 (DSRAM), 293.76 (BROM). The BROM ends at 310.446 µm, which leaves a 4.55 µm channel before the core edge (315). The die is unchanged at 320 × 300 µm.
- Run: `TARGET=finish ~/tools/logs/b3_flow.sh pnr_r5` (blocks + parent, floorplan → finish).

### pnr_r5: result (01:50–02:21, 30 min 05 s)
- Macro origins as planned: (5.616, 8.64), (143.424 / 181.008 / 218.592 / 256.176, 8.64), (293.76, 8.64).
- **PD-8 fixed**: global route completed with 0 `DRT-0073`; wirelength 531 233 µm; 4 min 44 s, peak 2.3 GiB.
- **Detailed route killed by the kernel OOM killer**: `Out of memory: Killed process 11994 (openroad) … anon-rss:7227140kB`,
  `make: do-5_2_route Error 247`. It ran at 16 threads (1212 % CPU); RSS swung 4.0–6.3 GiB; 60 % of
  iteration 0 was done with 8571 violations (normal for a first pass) after 3 min 37 s. WSL has
  7.4 GiB RAM + 2 GiB swap. The b3_flow memory guard (avail < 300 MiB **and** swap > 1900 MiB) didn't fire
  because swap peaked at 1.4 GiB; the kernel killed the process first.
- Per the standing rule (stop if a run is killed for OOM), the flow stops here pending the owner's decision.
  The proposed config-only retry is to resume from `5_1_grt.odb` with fewer router threads (`NUM_CORES`), with no WSL change.
